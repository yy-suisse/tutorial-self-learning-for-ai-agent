Plug-in patterns: how the base loop composes

The base loop (boxes 1–4 above) is the elementary unit. Each pattern wraps it or changes one line inside it. BASE LOOP marks where the unchanged loop runs.

Planning: plan → execute → synthesize

Planner LLM — one call, no tools. Prompt: "break the task into an ordered JSON list"
↓ json.loads → [subtask 1 … n] (parse fails → plan = [task])
for each subtask, in order:
BASE LOOP — fresh messages, sees only its own subtask text
↓ collect results[i] (each is a string)
Synthesizer LLM — one call, no tools: task + all results → final answer

Subtasks are isolated: safe only if independent. Dependencies need depends_on + passing earlier results in.

Critic: generate → judge → revise

BASE LOOP → answer
↓ answer only — the critic never sees the loop's reasoning or tool calls
Critic LLM — fresh context: task + answer, no tools, no history → pass / fail + feedback
↓ pass → return answer  |  fail ↓
append to the agent's messages: assistant(answer), user("Reviewer found: … Revise.")
BASE LOOP revises (same agent, same tools, same history)

Bounded by MAX_REFLECTION_ROUNDS; the last revision is returned unchecked. Critic JSON that fails to parse counts as pass.

Parallel calls: inside one turn

reply arrives with k tool_calls (k ≥ 1)
append the assistant message (all k calls) first
↓ start all k together
await asyncio.gather(execute(c) for c in calls) — semaphore caps concurrency
↓ k results, in request order (zip pairs result ↔ call.id)
append k tool messages → next turn

Changes only the tool-execution lines. Turns stay sequential; time ≈ slowest call, not the sum. Only helps for I/O-bound tools.

Multi-agent: a tool is another loop

Orchestrator BASE LOOP — tools = delegate_to_researcher, delegate_to_writer
↓ a tool call starts a sub-agent
Researcher BASE LOOP — own prompt, own registry: search, calculate
Writer BASE LOOP — own prompt, no tools
↓ only the final string returns, as an ordinary tool result
orchestrator appends assistant(tool_calls) + tool(result), loops on

Each agent sees only its own tool registry and its own messages. Sub-agents have no delegate tools, so depth stays at 2.

How messages evolves, turn by turn

Worked example: "What is (438 × 12 − 57) / 3?" with a calculate tool. + marks what that turn appends. The list only grows, and the LLM re-reads all of it on every call (until context management compresses it).

Start — 2 messages
{role: "system", content: "You are an agent. Use the tools when needed."}
{role: "user", content: "What is (438*12 - 57) / 3? Give just the number."}
Turn 1 — LLM sees 2 messages → reply HAS tool_calls → append 2 → 4 messages
+ {role: "assistant", content: null, tool_calls: [{id: "c1", function: {name: "calculate", arguments: '{"expression": "((438*12)-57)/3"}'}}]}
+ {role: "tool", tool_call_id: "c1", content: "1733.0"}
Turn 2 — LLM sees 4 messages → reply has NO tool_calls → return, append nothing
{role: "assistant", content: "1733"}  ← the answer is in content; the loop returns it

Role colors: system user assistant tool

  • Assistant reply with tool_calls: appended as-is. Its content is often null — the "action" lives in tool_calls, and the arguments are a JSON string.
  • One tool message per tool_call_id, content always a string — even for errors ("ERROR: …") and skipped calls ("SKIPPED: …"). An unanswered id makes the API reject the next call.
  • Final assistant reply: no tool_calls, answer in content. Nothing more needs appending — the loop returns. Tool results never move into content; they stay in the tool messages, and the model rewrites the answer from them.
  • In a no-tools loop (module 1): the turn appends the assistant text, then a user "Continue…" nudge — that user message plays the role the tool result plays here: new input that drives the next turn.

Trap: one tool needs another tool's result

All tool_calls in a reply are written before any result exists. If tool B's argument depends on tool A's result, the model can only guess it. Example from the MCP tutorial (word_count, then add):

+ {role: "assistant", tool_calls: [ {id:"c1", word_count(text:"…")}, {id:"c2", add(a: 0 ← guessed, b: 5)} ]}
+ {role: "tool", tool_call_id: "c1", content: "42"}
+ {role: "tool", tool_call_id: "c2", content: "5"}  ← valid-looking but wrong: built from the guess
  • Independent calls in one reply are fine — that is exactly what parallel calling is for.
  • Dependent calls must span two turns: call A → append its result → the LLM reads it → call B. A large model usually does this by itself; a small model often emits both calls at once and guesses.
  • Defense 1 — prompt: "Call one tool at a time. Wait for its result before deciding the next call." A prompt is a request, not enforcement.
  • Defense 2 — code constraint: execute only the first call of the reply; answer every other call with "SKIPPED: one tool per turn, call it again after seeing this result." Every tool_call_id still gets its tool message.
  • Defense 3 — API flag: parallel_tool_calls=False where supported (it had no effect on the local Ollama server in the tutorial — hence defense 2).
  • Why validation doesn't save you: it checks types, not values. A guessed a=0 is a perfectly valid number. Only sequencing fixes this.

Source: tuto/13_mcp_exampe.ipynb · tuto/8_parallel_tool_calling.py

What gets appended each turn

Only the reply's tool_calls decide which case you are in.

Case A: reply has tool_calls

  1. Append the reply (role assistant, with tool_calls).
  2. For each call, append one tool message with the same tool_call_id.
  3. Loop back. The LLM now sees the results.

Case B: no tool_calls

  1. Nothing else is appended.
  2. Return message.content as the final answer.

Tool results are never inside message.content. They sit in the tool messages. The final text is the model's summary of them, so it may not cover every result.

2. Running a tool call

  • The arguments arrive as a JSON string.
  • json.loads turns it into a dict; fn(**args) runs the function.
  • Convert the return value to a string, then append it as a tool message.
args = json.loads(call.function.arguments)    # JSON string → dict
result = TOOL_REGISTRY[name](**args)          # dict → Python call
messages.append({"role": "tool",
                 "tool_call_id": call.id,
                 "content": str(result)})     # → string

Source: tuto/2_single_tool.ipynb, tuto/3_tool_call_full.ipynb

3. Errors become strings

  • execute_tool_call never raises. The model reads the error and can try again.
  • Unknown tool, bad JSON, bad arguments, and a crash inside the tool each return their own message.
  • Caveat: a TypeError raised inside the tool body looks like bad arguments. Check with inspect.signature(fn).bind(**args) first.
fn = TOOL_REGISTRY.get(name)
if fn is None:                     return "ERROR: unknown tool"
try: args = json.loads(call.arguments)
except JSONDecodeError:           return "ERROR: could not parse arguments as JSON"
try:  return str(fn(**args))
except TypeError:                  return "ERROR: invalid arguments"
except Exception:                  return "ERROR: tool raised an exception"

Context management

  • system and task stay fixed.
  • summary holds older steps, rewritten by an LLM call.
  • recent_steps keeps the last K steps word for word.
  • Each turn: compress old steps, build the messages, call the LLM.
messages = [system, user(task)]
+ [summary]            if any
+ flatten(recent_steps)

Persistent memory

  • Facts live in a JSON file (key → fact). Each run starts fresh; only the file carries over.
  • Tools: read_memory, remember, forget.
  • Writes go to a temp file, then replace the old one, so a crash cannot corrupt it.

Planning

  • Plan: one LLM call, no tools, returns a JSON list of subtasks.
  • Execute: each subtask runs its own small tool loop.
  • Synthesize: one LLM call combines the results.
  • Real systems add depends_on and run independent steps in parallel.

Error recovery and reflection

  • Retry limit: after N consecutive ERROR: results for one tool, block that tool.
  • Critic: a fresh LLM call (task + answer, no tools) returns pass or fail. On fail, its feedback goes back to the agent.
  • Every loop has a cap (turns, failures, reflection rounds).

Parallel tool calls

  • Calls in one reply run together with asyncio.gather. Results keep the request order.
  • An asyncio.Semaphore caps how many run at once.
  • Append the assistant message with all tool_calls first, then one tool message per call.
  • Only helps when tools wait on I/O. The loop stays sequential across turns.
results = await asyncio.gather(*(execute_tool_call(c) for c in reply.tool_calls))
for call, result in zip(reply.tool_calls, results):
    messages.append({"role": "tool", "tool_call_id": call.id, "content": result})

Guardrails

  • Three layers in code, not in the prompt: validate arguments, confirm dangerous tools with a human, audit every attempt.
  • The developer sets dangerous=True. The LLM never sees this flag.
  • A denial goes back to the model as a normal tool message.

Observability

  • A Tracer records one llm_call per turn and one tool_call per requested tool.
  • Each event has a step, a type, a duration, and an is_error flag.
  • Use it to see whether slowness came from the model or from a tool.

Multi-agent

  • A sub-agent is a whole loop wrapped in a function. The orchestrator calls it like a tool.
  • Each agent has its own prompt, tools, and messages. Only the final text comes back.
  • Sub-agents have no delegate tools, so the depth stays at two.

Source: module11_multi_agent.py · tuto/11_multiagtens.py

MCP (Model Context Protocol)

  • MCP tools run in a separate server process. The agent is the client.
  • Steps: start the server, initialize(), list_tools(), convert to the LLM schema.
  • In the loop, only the tool-running line changes: await session.call_tool(name, args).
  • Check is_error. A failed call returns text, not an exception.
